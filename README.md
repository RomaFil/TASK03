# TASK03 — clang-format на реальному коді ядра Linux

## Навіщо це

`clang-format` — інструмент автоформатування C/C++-коду: він не шукає
логічні помилки, а лише перевіряє/приводить код у відповідність до правил
з файлу `.clang-format`. Питання, яке перевіряє цей репозиторій:

- Наскільки різним буде результат форматування, якщо запустити **різні
  версії** clang-format на одному й тому самому коді з однаковим стилем?
- Наскільки різним буде результат, якщо лишити версію тулу незмінною, але
  підмінити **базовий стиль** (наприклад, з Linux kernel на Chromium)?

Питання не абстрактне: у реальній команді / CI, якщо в різних розробників
або на різних серверах стоять різні версії clang-format, лінтер може
показувати різні результати на одному й тому самому коді — і незрозуміло,
хто "правий".

## Як влаштований експеримент

Замість вигаданого прикладу коду взято **реальні файли з ядра Linux**
(`torvalds/linux`, гілка master) — вони вже написані під конкретний
kernel-style, тож будь-які розбіжності при перевірці — це або справжня
специфіка версії тулу, або справжня специфіка стилю, а не випадковість.

**Обрані файли** (`dummy/`, мікс `.c`/`.h`, кілька директорій, сума > 100 КБ):
`fs/ext4/inode.c`, `fs/btrfs/qgroup.{c,h}`, `fs/btrfs/raid56.{c,h}`,
`drivers/scsi/megaraid/megaraid_mm.{c,h}`.

**Дві версії clang-format:**
- `XX = clang-format-17` (нативний пакет Ubuntu apt)
- `YY = clang-format-23` (через pip в ізольованому venv)

**Скрипти:**
- `check_format.sh <dir>` — перевіряє стиль обома версіями (`--dry-run
  --Werror`), нічого не змінює на диску, лише показує розбіжності.
- `make_format_XX.sh <dir>` / `make_format_YY.sh <dir>` — форматують файли
  на місці (`-i`) версією 17 / 23 відповідно.

## Що вийшло

1. **Перша перевірка сирого коду ядра проти його ж `.clang-format`** —
   2522 знайдені розбіжності. Це нормально: код писався роками різними
   людьми, і навіть "рідний" clang-format-конфіг ядра не покриває все
   ідеально (є нюанси, які clang-format не вміє відтворити — вирівнювання
   коментарів, macro continuation тощо).

2. **Автоформатування версією 17** прибрало всі 2522 розбіжності
   (1405 вставок / 1219 видалень по файлах). **Те саме форматування версією
   23 поверх уже відформатованого коду** змінило лише 2 рядки. Тобто **між
   версіями 17 і 23 різниця в результаті форматування мінімальна** — стиль
   майже повністю визначається `.clang-format`-файлом, версія самого
   інструменту впливає слабо.

3. **Заміна базового стилю на Chromium** (той самий код, той самий
   clang-format-17) дала diff у 14035 вставок / 15043 видалень —
   переформатування практично всього коду. Це на порядок більше за різницю
   між версіями. Тобто **вибір базового стилю впливає на результат набагато
   сильніше, ніж версія тулу**.

4. **Несподіваний і, мабуть, найцікавіший результат**: коли `.clang-format`,
   згенерований версією 23 (`--dump-config`), спробували прочитати версією
   17 — вона просто відмовилась працювати: `error: unknown key
   'EnumAssignments'`. Новіша версія clang-format додала новий ключ
   конфігурації, якого старіша версія не знає, і замість дрібної
   розбіжності у форматуванні стався **повний збій парсингу файлу**.
   Практичний висновок: у команді/CI критично важливо фіксувати **одну**
   конкретну версію clang-format — конфіг, згенерований новішою версією,
   може повністю зламати перевірку на старішій.

## Як відтворити

./make_format_XX.sh dummy      # форматує версією 17
./make_format_YY.sh dummy      # форматує версією 23
