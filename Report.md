
## Порівняння версій clang-format (17 vs 23)

- clang-format-17 на неформатованому коді: 2522 знайдені порушення стилю (`check_format.sh`), виправлено автоформатуванням (`make_format_17.sh`) — 1405 insertions / 1219 deletions.
- clang-format-23 поверх уже відформатованого версією 17 коду: лише 2 insertions / 2 deletions.
- Висновок: між версіями 17 і 23 форматування практично ідентичне — стиль детермінований `.clang-format`-файлом, версія самого інструменту впливає мінімально.

## Фінальна валідація

- До форматування: 2522 порушення (check_format.sh на сирих файлах ядра).
- Після make_format_17.sh + make_format_23.sh: 4 залишкові діагностики.
- Усі 4 — в одному файлі, `dummy/include/raid56.h`, рядки 267-268:
dummy/include/raid56.h:267:30: error: code should be clang-formatted
dummy/include/raid56.h:267:32: error: code should be clang-formatted
dummy/include/raid56.h:268:30: error: code should be clang-formatted
dummy/include/raid56.h:268:32: error: code should be clang-formatted

- Причина: clang-format-17 не погоджується з clang-format-23 щодо пробілів усередині виразу `((u64)-2)` / `((u64)-1)` (макроси `RAID5_P_STRIPE` / `RAID6_Q_STRIPE`) — граничний випадок, де правила форматування castів відрізняються між версіями. Не реальна помилка стилю, а різниця версій інструменту.

## Дослідження стилю Chromium (Крок 6)

### Дефолтні конфіги Chromium
Отримано `--dump-config` для обох версій: `chromium-XX.clang-format` (17) і
`chromium-YY.clang-format` (23) — дефолтні налаштування стилю Chromium уже
різняться складом ключів між версіями (підтверджено нижче помилкою парсингу).

### Перехід dummy на Chromium-стиль
- **clang-format-17 + Chromium-конфіг**: 14035 insertions / 15043 deletions
  на 8 файлах — це заміна ~100% форматування. Для порівняння: перехід з
  "сирого" коду на LLVM/Linux-стиль (Крок 5) дав 1405/1219. Тобто **зміна
  базового стилю (LLVM/Linux → Chromium) впливає на код на порядок сильніше**,
  ніж зміна версії clang-format у межах одного стилю — Chromium: 2-пробільні
  відступи без табів, ColumnLimit 80, інший стиль дужок.
- Перевірка після: `check_format.sh` — clang-format-17 знаходить 0 розбіжностей
  (самоузгоджено, форматували щойно ним же), clang-format-23 знаходить ті самі
  4 залишкові діагностики на `raid56.h:269-270` (`((u64)-2)` / `((u64)-1)`) —
  ідентичний патерн версійного дрейфу, що й у LLVM-стилі (Крок 5). Це підтверджує:
  розбіжність round у castах усередині макросів — системна відмінність 17 vs 23,
  а не особливість конкретного base-стилю.

- **clang-format-23 + Chromium-конфіг (поверх стану 17)**: diff 127/19,
  переважна частина (142 рядки) — зміни в самому файлі `.clang-format`
  (різний набір ключів між дефолтними дампами 17 і 23), лише 4 рядки — той
  самий `raid56.h`.
- Перевірка після: clang-format-23 — 0 розбіжностей. clang-format-17 —
  **не пройшла: `error: unknown key 'EnumAssignments'`, `Error reading
  .clang-format: Invalid argument`**. Це не діагностика стилю, а повний збій
  парсингу конфіг-файлу: ключ `EnumAssignments` з'явився у clang-format між
  версіями 17 і 23, і старіший бінарник взагалі не вміє прочитати конфіг,
  згенерований новішим.

### Головний висновок

1. **Вибір базового стилю (LLVM/Linux vs Chromium) — вирішальний фактор**:
   різниця в тисячі рядків, тоді як різниця між версіями clang-format у межах
   одного стилю — одиниці рядків (граничні випадки на кшталт cast-виразів
   у макросах).
2. **Несумісність версій буває не лише "косметичною"**. Формат самого
   `.clang-format` еволюціонує разом з інструментом: конфіг, згенерований
   новою версією (23), може містити ключі, яких стара версія (17) не знає
   — і замість дрібних розбіжностей у форматуванні отримуємо **повний
   збій виконання**. Практичний висновок: у CI/CD (див. [[Стиль коду в C — K&R, Linux kernel, GNU, clang-format і CI]])
   потрібно фіксувати ОДНУ конкретну версію clang-format для всього проєкту,
   а не покладатись на "будь-яку доступну" — інакше конфіг, створений
   розробником з новішою версією, зламає перевірку в іншого з застарілою.
